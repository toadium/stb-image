  - task_v1.md 第 25 行明确要求"章节标题层级与现有 ROADMAP.md 保持一致（一级标题为文档标题，二级标题为版本/章节分节）"，且"内容可直接替换或追加到 ROADMAP.md 中而不破坏现有锚点结构"。
  - 现有 ROADMAP.md 中版本为二级标题（`## v1.1`、`## v2.0` 等，共 20 处），章节亦为二级标题（`## 现状定位`、`## 不做的事情` 等）。

  - 直接追加到 ROADMAP.md 会出现 `## v1.17`（二级）后跟 `### v1.18`（三级）的层级错乱，破坏锚点结构，不满足"格式兼容"约束。do_v1.md 第 46 行声称"与现有 ROADMAP.md 标题层级一致"，与实际不符。

- **[一般] v1.20 两处对 `info_from_path` raise 声明是否算签名变更的表述自相矛盾**
  - 第 125 行功能项 3 风险点："中：签名变更，需更新调用方"。
  - 第 141 行交付物清单："公开函数数变化：0（只改实现，不改签名；`info_from_path` 增加 raise 声明不算签名变更）"。
  - 同一变更一处称"签名变更"，一处称"不算签名变更"，结论互斥。且增加 raise 声明实质改变了调用方需处理的错误契约，与"v1.0 API 冻结（只增不改）"约束存在张力，需明确此为"修正"还是"变更"并统一口径。

- **[一般] 多个版本"合并理由"引用的工作量与功能项表逐项加总不一致，合并原则论证基础自相矛盾**
  - 合并原则（第 281-284 行）要求"合并后总工作量不超过 L（≤10 人日）"，合并理由均以 P 原估算论证符合该原则，但功能项拆分后逐项加总已超 L：
    - v1.19（第 79 行）称"合并后 6-10 人日落在 L 范围内"，但 9 个功能项（8S+M）按口径下限 11 人日、上限 21 人日，已超 L。
    - v1.20（第 117 行）称"合并后 5-8 人日落在 L 范围内"，但 8 个 S 项加总 8-16 人日，上限超 L。
    - v1.18 共 7 个 S 项加总 7-14 人日，远超 P0 原估算 2-3 人日；v2.0 功能项加总约 26-44 人日，远超 P6 原估算 10-15 人日。
  - 粗粒度 P 估算与细粒度功能项拆分存在差异本可接受，但 iteration_plan 未说明差异原因，且用 P 原估算论证"符合合并原则"而功能项加总却违反该原则，论证基础与实际拆分自相矛盾。

- **[轻微] v1.20 功能项 8 与 v1.18 功能项 4 冗余重叠**
  - v1.18 项 4 已明确"修正 ARCHITECTURE.md：补充 process/ 的 7 个子子包结构"。
  - v1.20 项 8"补充 ARCHITECTURE.md 中 process 子包结构描述（若 v1.18 未完成）"以条件化处理，但 v1.18 已确定包含此项，该条件分支实际为死代码，使 v1.20 工作量评估含不确定性。应移除或明确触发条件。

## 修改要求

1. **[严重] 版本标题层级不一致**：
   - 问题：iteration_plan.md 版本用三级标题（`### v1.18`），现有 ROADMAP.md 版本为二级标题（`## v1.1`），违反"格式兼容"约束。
   - 为什么是问题：task_v1.md 第 25 行是明确约束，do_v1.md 声称层级一致但实际不符，直接替换会破坏 ROADMAP.md 锚点结构。
   - 期望修正方向：将版本标题从三级（`### v1.18`）提升为二级（`## v1.18`），版本下的"功能项""测试与验证要求"等子节相应下调一级（原二级章节"计划概述"等可保持二级，与 ROADMAP.md"现状定位""迭代原则"等章节并列；版本作为二级标题与 ROADMAP.md `## v1.1` 一致）。修正后核实 do_v1.md 第 46 行的格式兼容性声明。

2. **[一般] `info_from_path` raise 声明口径矛盾**：
   - 问题：第 125 行称"签名变更"，第 141 行称"不算签名变更"，结论互斥。
   - 为什么是问题：同一变更两处结论互斥，审阅者无法判断是否影响 v1.0 API 冻结承诺。
   - 期望修正方向：统一口径。建议明确"增加 raise 声明属于 API 契约变更，但属'修正使与 info_from_bytes 一致'，归入错误处理修正范畴，需在 CHANGELOG 标注"，并据此修正第 125 行风险点和第 141 行交付物清单两处表述，使其一致。

3. **[一般] 合并理由工作量论证与功能项加总不一致**：
   - 问题：合并理由用 P 原估算论证"符合合并原则（≤L）"，但功能项逐项加总超 L，论证基础自相矛盾。
   - 为什么是问题：合并原则是版本规划的决策依据，论证基础与实际拆分不一致会误导审阅者对合并合理性的判断。
   - 期望修正方向：二选一——(a) 在合并理由中改用功能项逐项加总作为论证基础，若超 L 则说明为何仍可合并（如"细粒度拆分后偏高，但 P1+P2 粗粒度估算 6-10 人日仍为合并决策依据"）；(b) 重新评估各功能项工作量使其与 P 原估算对齐。同时建议在 v1.18、v2.0 等版本补充说明功能项加总与 P 原估算差异的原因。
