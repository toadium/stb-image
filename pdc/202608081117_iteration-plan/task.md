## 任务目标

基于上一轮审查报告的结论与建议，结合现有 ROADMAP.md、ARCHITECTURE.md、COMPARISON.md 等文档，整理一份结构化的迭代计划文档，供用户审阅。

## 产出要求

产出一份迭代计划文档（Markdown），应包含以下内容：

### 1. 计划概述
- 计划制定日期、基于的审查报告路径、当前版本基线
- 计划的总目标和阶段性愿景

### 2. 迭代版本规划
按版本号组织（如 v1.18、v1.19、v2.0 等），每个版本包含：
- **版本目标**：一句话描述该版本要达成的目标
- **功能项**：具体要实现的功能列表，每项含：
  - 功能名称
  - 实现方式（FFI / 纯 MoonBit / 架构改动）
  - 涉及的子包（core/process/format/meta/util）
  - 工作量评估（S/M/L/XL）
  - 优先级（高/中/低）
  - 风险点
- **测试与验证要求**：新增测试数、ASan 验证范围、基准测试
- **交付物清单**：新增/修改的文件、公开函数数、类型数变化
- **依赖关系**：是否依赖其他版本先行完成

### 3. 优先级排序说明
- 解释为什么这样排序（动机、价值、风险、成本权衡）
- 与审查报告中"推荐的下一步行动"的对应关系

### 4. 风险与缓解措施
- 汇总各版本的主要风险
- 给出缓解措施

### 5. 不做的事情（明确排除项）
- 沿用并更新 ROADMAP.md 中的"不做的事情"清单
- 说明排除理由

### 6. 与现有 ROADMAP.md 的差异说明
- 本计划与现有 ROADMAP.md 的主要差异点
- 哪些项被调整了优先级、哪些是新增、哪些被移除或推迟

### 7. 审阅检查清单
- 列出需要用户确认的关键决策点（如：v2.0 路径 A vs B、是否纳入某功能等）
- 列出需要用户确认的优先级排序

## 约束

1. 计划必须基于审查报告的结论，不得凭空捏造方向
2. 每个功能项必须可执行、可验证，避免模糊描述
3. 必须保持 v1.0 API 冻结原则（只增不改）
4. 必须考虑五子包架构的约束
5. 产出文件应可直接作为新的 ROADMAP.md 候选内容（格式兼容）
6. 计划应覆盖短期（下 1-2 个版本）、中期（3-5 个版本）、长期（v2.0+）三个时间尺度

## 输出位置

迭代计划文档输出到工作目录下的 `iteration_plan.md`。
